# 🗄️ Migrations with Alembic

**Status:** ✅ Done and verified (2026-07-24) · **Priority:** High · **Effort:** M (1-3 days) · **Dependencies:** None

## Why
Today the schema is created with `Base.metadata.create_all` on backend startup. That doesn't version anything: any change to the models (a new column, an index, a rename) doesn't get applied to existing databases and breaks real deployments. Without migrations there's no serious production setup nor safe schema evolution.

## Scope
**Includes:**
- Initialize Alembic with `env.py` pointing to `app.database.Base.metadata` and `settings.database_url`
- Initial autogenerated migration of the current schema (households, users, invitations, accounts, categories, transactions, attachments, recurring_rules)
- Remove `create_all` from `main.py` in production (or keep it only for tests)
- Automatic migrations on backend startup in Docker (entrypoint or command)
- Document the workflow (`uv run alembic revision --autogenerate`, `uv run alembic upgrade head`)

**Doesn't include:**
- Data migrations beyond the initial schema
- Support for downgrade in production as a normal flow (it gets implemented, but not automated)
- Migration branching/merging tools for multiple developers

## Proposed design

### Backend
- `uv add alembic` and `alembic init alembic`
- `alembic/env.py`: import `Base` from `app.database` and read the URL from `app.core.config.settings.database_url` (don't hardcode it in `alembic.ini`)
- Generate the initial migration: `uv run alembic revision --autogenerate -m "initial schema"` against an empty DB; manually review that the 8 tables come out correctly
- Remove `Base.metadata.create_all(bind=engine)` from startup in `main.py` (lifespan/startup)
- Tests: keep `create_all` in the test fixture (in-memory SQLite, faster and isolated); don't touch the 37 existing tests

### Frontend
- No changes

### Infra
- Backend in `docker-compose.yml`: change the command to something like `sh -c "alembic upgrade head && uvicorn app.main:app ..."` or an `entrypoint.sh` that runs migrations before starting uvicorn
- Verify that the ordering with `depends_on: db` is still sufficient (the migration must wait for Postgres to be ready; reuse the current wait mechanism if one exists)
- Document in the README: how to create a new migration after touching models and how to apply it in the self-hosted stack

## Acceptance criteria
- [x] `uv run alembic upgrade head` on an empty database correctly creates the 8 tables
- [x] `uv run alembic downgrade base` reverts the initial migration without errors
- [x] After a test change to a model, `alembic revision --autogenerate` detects the diff and generates the migration (verified with the onboarding column, doc 05)
- [x] The Docker stack starts with an empty DB and applies migrations on its own (without `create_all`)
- [x] The 37 pytest tests keep passing without logic changes

## What was implemented (2026-07-24)

- `backend/alembic/env.py`: reads `Base.metadata` from `app.database` and imports `app.models`;
  the URL comes from `settings.database_url` (`alembic.ini` is left with
  an empty `sqlalchemy.url`, the file is committed). `render_as_batch` only on SQLite.
- `alembic/versions/5d15cfc79c35_esquema_inicial.py`: the 8 tables. Reviewed
  by hand: autogenerate had rendered the `created_at` columns as
  `sa.text('(CURRENT_TIMESTAMP)')` (a literal from the dialect it was generated with) and
  the indexes in batch mode; these were changed to `sa.func.now()` and `op.create_index`
  so the result is identical on Postgres and SQLite.
- `app/main.py`: `create_all` removed.
- `app/db_bootstrap.py` + `entrypoint.sh`: the container migrates before uvicorn.
  **Bridge for pre-Alembic databases:** if it finds the tables without
  `alembic_version` (created by the old `create_all`), it stamps the
  initial migration instead of re-creating them — without this, the current
  deployment's database would blow up with "table households already exists". Idempotent.
- `Dockerfile`: copies `alembic/`, `alembic.ini` and `entrypoint.sh`.
- `backend/README.md`: workflow documented.

**Verified on SQLite:** `upgrade head` → 8 tables + `alembic_version`;
`alembic check` → no diff against the models; `downgrade base` → clean;
bootstrap on a fresh database, on a legacy database made with `create_all` (stamps,
doesn't re-create) and on a second startup (no-op). The 37 tests pass.

**Verified on Postgres with the stack running (2026-07-24):**
- The bridge did its job against the real database: container log →
  `Database created before Alembic: stamping it at 5d15cfc79c35 without re-creating tables`
  → `Running upgrade 5d15cfc79c35 -> 673ed5f3d911`. `alembic_version` ended up at
  `673ed5f3d911` and the data intact (4 transactions, 4 accounts, 30 categories,
  2 attachments, 3 households).
- Empty Postgres database (temporary database `budget_migration_check`, already deleted):
  `upgrade head` → the 8 tables + `alembic_version`, `alembic check` with no diff,
  `downgrade base` clean.

- Main risk: the autogenerated initial migration might not exactly match what `create_all` produced (indexes, constraints). Review the diff by hand before committing it.
